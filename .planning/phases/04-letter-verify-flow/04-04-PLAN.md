<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → verify-email | Token (untrusted string from URL) crosses the boundary; anon key in Authorization header is public |
| verify-email → app_private | seal_letter_with_token is the only path — app_private is sealed from Data API |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-18 | Spoofing | verify-email: token as bearer credential | mitigate | Token is 256-bit CSPRNG hex; validate inside the seal RPC (not in the Edge Fn); no additional auth header needed — token IS the credential (RESEARCH Pitfall 9) |
| T-04-19 | Tampering | verify-email: double-seal | mitigate | seal_letter_with_token uses FOR UPDATE on token row; second call returns 'already_sealed' before any mutation |
| T-04-20 | Information Disclosure | verify-email: token in logs | mitigate | Only `{ state: sealState }` is logged — raw token value never appears in console.log or console.error |
| T-04-21 | Elevation of Privilege | verify_jwt=false | mitigate | verify_jwt=false is correct (all functions in this project use it — browser calls anon JWT, not service-role); auth truth is inside the seal RPC, not the gateway |
| T-04-22 | Repudiation | no email sent from verify-email | mitigate | EMAIL-B2: explicitly no sendResendEmail; sealed confirmation is the /verify page state, not a follow-up email — prevents spurious sends |
| T-04-23 | Denial of Service | open POST to verify-email | accept | Token must be guessed (256-bit CSPRNG); invalid guesses return 'invalid' cheaply; per-IP rate limit not required for v1 |
</threat_model>
