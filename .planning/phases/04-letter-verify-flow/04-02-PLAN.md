  `const SUPABASE_URL = '%VITE_SUPABASE_URL%'` — Vite replaces `%VITE_*%` tokens in
  HTML files during build. This is the correct approach for multi-page Vite.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → verify-email Edge Fn | Token value crosses from client (URL query param) to server; anon key is public but must not be confused with the service role key |
| User → /verify URL | Anyone who guesses or enumerates token values would need a 256-bit CSPRNG hit — handled by the RPC, not the HTML page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-08 | Spoofing | verify.html token read | mitigate | Token validation occurs server-side in seal_letter_with_token (T-04-01/02); the HTML page is a dumb passthrough — it cannot validate the token itself |
| T-04-09 | Information Disclosure | verify.html inline script | mitigate | Script logs only `{ state }` — never logs the raw token value; anon key is already public (bundled in the React SPA) |
| T-04-10 | Information Disclosure | Vite %VITE_SUPABASE_URL% replacement | mitigate | Only public values (URL + anon key) are injected; VITE_SUPABASE_SERVICE_ROLE_KEY must never be in .env.local's VITE_ namespace |
| T-04-11 | Denial of Service | /verify endpoint (open GET) | accept | No auth required; token is a 256-bit secret; function call is fast (single RPC); no rate limit needed at v1 — add if abuse appears |
| T-04-12 | Tampering | already_sealed presented as error | mitigate | CONTEXT Discretion: already_sealed MUST render as success state, not error — prevents user confusion on double-click and avoids implying the flow failed |
</threat_model>
