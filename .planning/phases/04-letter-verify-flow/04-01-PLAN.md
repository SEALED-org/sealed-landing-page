<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Edge Function → DB | RPCs receive p_token (string) and p_user_id (uuid) from the Edge Function; app_private is never reachable from the Data API |
| DB internal | app_private.letters, schedules, verification_tokens are sealed — only SECURITY DEFINER wrappers can touch them |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | seal_letter_with_token | mitigate | `FOR UPDATE` on token row serializes concurrent seal attempts; used_at check prevents replay; both in one plpgsql transaction |
| T-04-02 | Spoofing | seal_letter_with_token | mitigate | Token is 256-bit CSPRNG hex (gen_random_bytes(32)); unknown token returns 'invalid'; no enumeration possible via timing (lookup is indexed by unique token) |
| T-04-03 | Tampering | seal_letter_with_token | mitigate | Token is per-user (no letter_id param); ownership chain enforced: token → user_id → letter.user_id — a holder of one user's token cannot seal another user's letter |
| T-04-04 | Tampering | upsert_pending_letter | mitigate | p_body is inserted as a parameterized text value (no dynamic SQL); DB CHECK(char_length(body) <= 2000) rejects oversized bodies even if Edge Fn cap is bypassed |
| T-04-05 | Information Disclosure | app_private schema | mitigate | Both RPCs use SET search_path=''; REVOKE ALL FROM public; GRANT only to service_role — Data API cannot reach app_private |
| T-04-06 | Repudiation | upsert_pending_letter | accept | No separate audit log for letter upserts in v1; letters.created_at + verification_tokens.used_at provide adequate trail for dispute resolution |
| T-04-07 | Elevation of Privilege | SECURITY DEFINER | mitigate | SET search_path='' prevents search_path injection; REVOKE from public eliminates unauthenticated invocation |
</threat_model>
