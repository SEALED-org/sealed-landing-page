### Section 3 — Counter (5-digit flip-card) — lifted-verbatim CSS plus inline JS

This is the most novel piece of the prototype. **HOW IT'S BUILT:** Pure CSS with hand-rolled inline JavaScript. **No GSAP. No motion library.** Plain `setTimeout` + class toggle.

**Markup pattern:** Lines 1379–1391. Five `<div class="digit"><span class="d-cur">N</span><span class="d-next">N</span></div>` cells inside `<div class="digit-row" id="count" aria-label="Sign ups so far">`. Label sibling: `<div class="counter-label"><span class="dot"></span><span>Sign ups so far</span></div>`.

**CSS technique (lines 1257–1313):**
```css
.counter { display: inline-flex; flex-direction: column; align-items: center; gap: 14px; }
.digit-row { display: inline-flex; gap: 8px; }
.digit {
  position: relative;
  width: 44px; height: 60px;
  background: #fff;
  border: 1px solid var(--ink-10);
  border-radius: 8px;
  box-shadow: 0 1px 0 var(--ink-06), inset 0 -2px 0 rgba(0,0,0,0.03);
  overflow: hidden;
  font-family: var(--font-serif); font-weight: 400;
  font-size: 36px; line-height: 60px; text-align: center;
  color: var(--ink); letter-spacing: -0.01em;
}
.digit::after {  /* hairline at 50% — the flip seam */
  content: ''; position: absolute; left: 6px; right: 6px; top: 50%;
  height: 1px; background: var(--ink-06); pointer-events: none;
}
.digit .d-cur, .digit .d-next {
  position: absolute; inset: 0;
  display: flex; align-items: center; justify-content: center;
}
.digit .d-next { transform: translateY(100%); }  /* below frame, ready to come up */
.digit.flip .d-cur  { animation: digitOut 0.5s cubic-bezier(0.7,0,0.3,1) forwards; }
.digit.flip .d-next { animation: digitIn  0.5s cubic-bezier(0.7,0,0.3,1) forwards; }
@keyframes digitOut {
  0%   { transform: translateY(0);     opacity: 1; }
  100% { transform: translateY(-100%); opacity: 0; }
}
@keyframes digitIn {
  0%   { transform: translateY(100%);  opacity: 0; }
  100% { transform: translateY(0);     opacity: 1; }
}
@media (max-width: 480px) {
  .digit { width: 38px; height: 52px; font-size: 30px; line-height: 52px; }
}
```
The `.counter-label .dot` (lines 1300–1305) is a rotated 5×5 ink-35 square: `transform: rotate(45deg)`.

**JavaScript (lines 1774–1801):** Plain DOM manipulation. Algorithm per digit:
1. `next.textContent = ch` (set the incoming character in the hidden `.d-next` element)
2. `d.classList.remove('flip'); void d.offsetWidth; d.classList.add('flip');` (force reflow so the animation re-fires)
3. `setTimeout(() => { cur.textContent = ch; d.classList.remove('flip'); }, 500)` (after the 500ms keyframe completes, copy the new char into `.d-cur` so the steady state is correct)

**No stagger in the prototype's `setCount` function.** The prototype animates all 5 digits simultaneously. The UI-SPEC and CONTEXT.md (`<specifics>` block) introduce a stagger pattern (`0ms, 40ms, 80ms, 120ms, 160ms`) that the React rewrite should add — this is an **enhancement** to the prototype, deliberately spec'd by UI-SPEC to "feel mechanical, not synchronous." Confirmed in CONTEXT.md `<specifics>` second bullet.

**Initial mount:** Prototype renders the digits hard-coded at `0 0 1 6 2` and then `setCount(count)` (where `count = 162`) is called only when the random interval bumps. The React rewrite should render `00000` on initial mount and animate to `target` (e.g., `00115`) on first paint — confirmed by UI-SPEC §"Component Contracts" → "On the initial mount, animate from 0 (so the first paint shows 00000 then ticks to 00115)."

**Width logic:** Always 5 cells, regardless of `target`. UI-SPEC: "the visual cell count is always 5 to match the prototype's fixed-width counter." Current `src/components/Counter.tsx` has `width = target >= 10000 ? 5 : ...` — keep this only to gate the `padStart` width, NOT to determine how many `.digit` elements to render. Render 5 always.

**Increment animation (during a `+1` bump):** Only digits that change flip. The prototype's `setCount` has `if (cur.textContent === ch) return;` (line 1784) — exact-match short-circuit.

**Out of scope for Phase 1.5:** The prototype's `setInterval(() => { if (Math.random() < 0.35) bumpCount(); }, 4200)` random bump (lines 1799–1801) — explicitly out per UI-SPEC §"Out of Scope" item 1.

**Animation:** `digitOut` and `digitIn` (both 500ms, `cubic-bezier(0.7,0,0.3,1)`, declared `forwards`). Pure CSS.

**Assets used:** None.

function showStep(hideId, showId) {
  const hideEl = document.getElementById(hideId);

### Pattern 1 — Scroll reveal (`whileInView`)

**When to use:** Hero (`.hero-inner` — but the prototype tags `.in` immediately so this is optional), How cards (`reveal`, `reveal d1`, `reveal d2`), Research children (`reveal`, `reveal d1`, `reveal d2`), FirstLetter head (`reveal`), `.fl-stage` (`reveal d1`), `.fl-promise` (`reveal d2`).

**Skeleton (verified API per motion.dev/docs/react-scroll-animations):**
```tsx
<motion.div
  initial={{ opacity: 0, y: 20 }}
  whileInView={{ opacity: 1, y: 0 }}
  viewport={{ once: true, amount: 0.12 }}
  transition={{ duration: 0.9, ease: 'easeOut', delay: 0 /* or 0.08 for .d1, 0.16 for .d2 */ }}

```

**Why `viewport.amount: 0.12`:** The prototype's IntersectionObserver uses `threshold: 0.12` (Landing.html line 1956). Match it.

**Why `viewport.once: true`:** The prototype only adds `.in` once and then `io.unobserve(e.target)` (line 1955). Match it.

**Stagger delays:** `.reveal` = 0s, `.d1` = 0.08s, `.d2` = 0.16s, `.d3` = 0.24s (Landing.html lines 1328–1330). Pass via `transition.delay`.

**Alternative:** Keep the prototype's `IntersectionObserver` + CSS class-flip pattern instead of `whileInView`. UI-SPEC line 533 says either is acceptable. **Recommendation:** Use `whileInView` — it's React-idiomatic, plays well with StrictMode double-renders, and avoids manual IO cleanup. The `motion.div` doesn't need keys (no list); a stable mount is enough.

### Pattern 2 — Counter flip (NOT Motion — pure CSS)

**Do NOT use `useMotionValue`/`useTransform`/`animate`.** The current `src/components/Counter.tsx` does this; it's the **wrong pattern** for the new contract (UI-SPEC explicitly says "Avoid `useMotionValue` (the current odometer pattern is being replaced)").

**Skeleton (vanilla React + CSS class toggle):**
```tsx
import { useEffect, useRef, useState } from 'react';

interface CounterProps { target: number }

export default function Counter({ target }: CounterProps) {
  const [displayed, setDisplayed] = useState(0);
  const flipTimers = useRef<number[]>([]);

  useEffect(() => {
    setDisplayed(target);
  }, [target]);

  // displayed → string padded to 5 chars
  const chars = String(displayed).padStart(5, '0').split('');

  // On every render, schedule per-digit flips by comparing previous chars
  // (track previous in a ref to avoid re-firing on identical re-renders)
  // …details: toggle `.flip` class on each .digit that changed, with
  //  setTimeout staggered 0/40/80/120/160ms, remove after 500ms.

  return (
    <div className="counter">
      <div className="digit-row" aria-label="Sign ups so far">
        {chars.map((ch, i) => (
          <DigitCell key={i} char={ch} index={i} />
        ))}
      </div>
      <div className="counter-label">
        <span className="dot" aria-hidden="true" />
        <span>Sign ups so far</span>
      </div>
    </div>
  );
}
```

**DigitCell** holds previous char in a ref, swaps `.d-next` content, force-reflow (`void el.offsetWidth`), adds `.flip`, after 500ms copies `.d-next` → `.d-cur` and removes `.flip`. The CSS handles the actual translateY animation via `@keyframes digitOut`/`digitIn`.

**Stagger:** Use `setTimeout(() => triggerFlip(), 40 * index)` per digit so high-order settles last. UI-SPEC §"Component Contracts" line 466.

### Pattern 4 — FirstLetter step transitions (per D-01)

**Pure CSS classes.** No Motion. Match prototype byte-for-byte.

**Skeleton:**
```tsx
type Step = 'write' | 'email' | 'success';

const [step, setStep] = useState<Step>('write');
const [leavingStep, setLeavingStep] = useState<Step | null>(null);
const [enteringStep, setEnteringStep] = useState<Step | null>(null);

const transitionTo = (next: Step) => {
  setLeavingStep(step);
  window.setTimeout(() => {
    setStep(next);
    setLeavingStep(null);
    setEnteringStep(next);
    window.setTimeout(() => setEnteringStep(null), 400);

};

// Class assembly per step div:
const stepClass = (s: Step) => {
  if (s === leavingStep) return 'fl-step fl-step-leaving';
  if (s !== step) return 'fl-step fl-step-hidden';
  if (s === enteringStep) return 'fl-step fl-step-entering';
  return 'fl-step';
};

return (
  <div className="fl-stage">
    <div className={stepClass('write')}>...</div>
    <div className={stepClass('email')}>...</div>
    <div className={stepClass('success')}>...</div>
  </div>
);
```

The 300ms + 400ms timings match `stepOut` (300ms) and `stepIn` (400ms) keyframes exactly. The `.fl-step-hidden { display: none }` class keeps non-active steps out of the layout.

## Open Risks / Landmines

This section captures things that could break the build or trip up a careless plan.

### 1. Tailwind v4 `@theme` token consumption pitfalls

**Risk:** Tailwind v4 with the Vite plugin generates utilities from `@theme`-block vars at build time. Variable names must match conventions (`--color-X`, `--font-X`, `--text-X`, etc.) for utilities to be auto-generated. Custom names (e.g., `--ink-70`) won't produce utilities — they're only consumable as `var(--ink-70)`.

**Mitigation:** Decide upfront whether each token wants a generated utility or just a `var()` consumer:
- `--color-ink-70` (with the `--color-` prefix) → generates `text-ink-70`, `bg-ink-70`, `border-ink-70`.
- `--font-serif` (with the `--font-` prefix) → generates `font-serif`.
- `--text-mark` → generates `text-mark` utility (font-size).
- `--shell`, `--narrow` → no utility generation; consumed as `max-width: var(--shell)` in raw CSS.

Document the prefix conventions in the plan that adds the tokens.

**Verification:** After adding tokens, run `npm run build` and confirm the output `dist/assets/index-*.css` contains the expected utility class names (e.g., `.text-ink-70`).

### 2. TypeScript event types in form handlers

**Existing pattern (preserve):** `React.FormEvent` is used in `handleSubscribe` (`src/App.tsx:35`). Continue using `React.FormEvent` for form submit handlers. For textarea `onChange`, use `React.ChangeEvent<HTMLTextAreaElement>`. For input `onChange`, use `React.ChangeEvent<HTMLInputElement>`.

**Landmine:** React 19 + TypeScript 5.8 may show `React.JSX.IntrinsicElements` deprecation warnings if any inline-event signature is mis-typed. The current files all use the explicit annotation pattern — keep it.

### 3. Motion v12 `motion.div` JSX vs. `motion.create(...)`

**Risk:** Motion v12 changed the wrapper API. Older code used `motion.custom(Component)`; v12 uses `motion.create(Component)`. The lowercase JSX intrinsics (`motion.div`, `motion.span`, `motion.button`) still work as before — no changes.

**Mitigation:** Use `motion.div`, `motion.section`, `motion.button` in JSX directly. Don't wrap custom components with Motion in Phase 1.5 (none of the proposed components need it).

### 4. `dangerouslySetInnerHTML` for FAQ answers

**Risk:** ESLint `react/no-danger` rule (if added later) would flag this. The project currently has no ESLint config, but a future Phase 5 polish could add one.

**Mitigation:** Include an inline eslint-disable comment on the line that uses `dangerouslySetInnerHTML`:
```tsx
{/* eslint-disable-next-line react/no-danger */}
<div className="faq-a-inner" dangerouslySetInnerHTML={{ __html: faq.a }} />
```

Even though there's no ESLint config today, the comment serves as documentation that the choice is deliberate. The answers are developer-authored static strings — UI-SPEC line 582–583 explicitly approves this.

### 5. Special characters in JSX (the `&ensp;` problem)

**Risk:** The How step cards use `<span style="opacity:0.38">01</span>&ensp;Write a letter…` in the prototype. In JSX, you cannot write `&ensp;` directly — it's parsed as text. Options:

1. Use the Unicode literal: `<span style={{opacity: 0.38}}>01</span>{' '}Write a letter…`
2. Use the JSX entity escape: `<span style={{opacity: 0.38}}>01</span>{'  '}Write a letter…` (two non-breaking spaces — not equivalent, slightly tighter)
3. Use `dangerouslySetInnerHTML` for the entire h3 inner

**Recommendation:** Option 1 — `{' '}` is exactly an en-space, byte-equivalent to `&ensp;`. Don't substitute spaces.

### 6. React 19 StrictMode double-invocation of effects

**Risk:** The `App.tsx` already runs under `<StrictMode>` (`src/main.tsx:7–9`). React 19 + StrictMode double-invokes `useEffect` setup/teardown in development. The counter fetch (`getSignupCount().then(...).catch(...)`) runs twice in dev.

**Mitigation:** Not a problem in practice because:
- The fetch is idempotent (it's a read).
- `setWaitlistCount(115)` is also idempotent.
- The `AbortSignal.timeout(3000)` guards against runaway requests.

The Counter component's `useEffect` that schedules `setTimeout` flips needs cleanup — return a function that clears any pending timers. Pattern:
```tsx
useEffect(() => {
  const timers: number[] = [];
  // ... schedule flips, push timer ids ...
  return () => { timers.forEach(window.clearTimeout); };
}, [target]);
```

This was the bug pattern that made the existing Counter use `motion.useMotionValue` (which auto-cleans). The new vanilla approach needs explicit timer cleanup.

### 7. Auto-grow textarea

**Risk:** Setting `style.height = scrollHeight + 'px'` on every input event causes a synchronous reflow per keystroke. For a 5KB letter (~300 lines), this is a measurable ~5ms cost per keystroke. The prototype does this and it works fine.

**Mitigation:** Use the pattern verbatim. If performance becomes an issue (it won't for typical letters), switch to a `useLayoutEffect` that runs after the state update commits.

### 8. The `<p>` tag has nested `</p>` in Research section

**Risk:** Landing.html line 1517 has a stray `</p>` at the end of `.rs-kicker`. In JSX, this would be a syntax error.

**Mitigation:** Drop the stray tag. UI-SPEC's copy contract (line 239) doesn't include it.

### 9. The Section Divider has a stray `</div>`

**Risk:** Landing.html line 1403 has an extra `</div>` outside the wrapper. JSX won't parse this.

**Mitigation:** Drop it. The valid markup is `<div class="section-divider"><div class="inner"><span class="rule"/></div></div>`.

### 10. `.fl-pad-body` inline style overrides

**Risk:** Landing.html line 1551 has `<div class="fl-pad-body" style="padding-top: 8px; font-size: 22px; font-weight: 600">`. These inline styles don't match the CSS rule (lines 787–791) which sets no font-size or padding. They're real overrides that take precedence.

**Mitigation:** Replicate the inline styles in JSX: `<div className="fl-pad-body" style={{paddingTop: '8px', fontSize: '22px', fontWeight: 600}}>`. Note that `font-weight: 600` on the body cascades to the typewriter and textarea unless overridden — the textarea explicitly sets `font-weight: 400` via the `.fl-textarea` rule (line 808), so the cascade is benign.

### 11. Wax seal animation `transform: translateY(40px)` final state

**Risk:** The `.fl-wax-seal` rule (line 985–989) sets `transform: translateY(40px)` outside the keyframe. The keyframe ends at `translateY(40px)` too (line 994). So the seal's final resting position is 40px below the flap's center — this is intentional, matching the visual "seal sits on the bottom of the envelope back."

**Mitigation:** Preserve the rule and the keyframe verbatim. Do NOT "fix" it to translateY(0).

### 12. The `signup_counter` view must be reachable

**Risk:** STATE.md flags two `.env.local` issues (leading space in key, URL/JWT mismatch). If both are wrong, `getSignupCount()` will throw, the `.catch` fires, and the counter shows 115. UI still works. But it means the counter is "broken" in dev.

**Mitigation:** Phase 1.5 does not block on `.env.local` fixes. The verification check is "counter shows a number" — 115 is a valid number. If the planner wants to verify the live fetch path, fix `.env.local` first. Phase 2 will require it.

### 13. `npm run build` and Vite SSR

**Risk:** Vite 6 + React 19 + Tailwind v4 builds are stable, but `motion/react` v12 has had `"use client"` directive ambiguity in some bundlers when used in non-RSC contexts. The current project is purely client-side SPA (no SSR, no RSC), so no risk in practice.

**Mitigation:** Don't add `"use client"` directives. They're not needed.

### 14. Smooth scroll behavior across browsers

**Risk:** `document.getElementById('first-letter')?.scrollIntoView({ behavior: 'smooth' })` is well-supported, but Safari < 14 has bugs. The project doesn't have a stated browser-support floor. The prototype uses this pattern (line 1829).

**Mitigation:** Use the pattern verbatim. Phase 6 (Pre-launch QA) tests on iOS Safari and Android Chrome.
